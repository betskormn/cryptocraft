# CryptoCraft — план реалізації MVP

Мета MVP: робоча демонстрація для власників закладів — меню з біржовими цінами на TV, замовлення гостями через QR, кухня/бар бачать замовлення, рахунок закривається з фіскальним чеком.

Рухаємося по етапах зверху вниз. Відмічай `[x]`, коли пункт готовий і перевірений.

---

## Погоджені рішення

- **Ціна фіксується при відправці замовлення на кухню/бар** (не при додаванні в кошик); у цей момент позиція потрапляє в рахунок гостя.
- **Оплата в кінці візиту.** Кожен гість за столиком має власний рахунок; однаковий напій може мати різні ціни в різних позиціях.
- **QR на столику** відкриває сесію столика без реєстрації; користувач застосунку може прив'язати до неї свій акаунт (бонуси, знижки).
- **Склад як у більшості POS:** стоп-лист вручну + попередження, без жорсткого блокування продажів.
- **KDS:** кухня бачить `MEAL`, бар — `DRINK`, черга в порядку відправки.
- **Обвал ринку** запускає персонал кнопкою в адмінці; гостям — попередження про можливу затримку.
- **`min_price`** власник задає сам в адмінці.
- **Своя POS** (цільова аудиторія — малі заклади), з фіскалізацією через Checkbox.
- **Багато закладів (SaaS)** — обов'язково.
- **Формула динамічної ціни не визначена** — стратегія ціноутворення має бути змінною.
- **Пізніше:** оплата криптою, AI-движок ціноутворення, нативний застосунок vs PWA.

## Етап 4. Identity і безпека

**Частина 1 — персонал: готово**

- [x] **Identity Service** на Spring Authorization Server (OAuth2 / OpenID Connect): своя БД `identity`, сторінка входу, JWT (RS256, 10 хв) з закладами й ролями (`venues`, `platform_admin`), ключ підпису в БД, refresh-токени з ротацією; старий `authentication-service` видалено
- [x] **Персонал:** один акаунт на кілька закладів, у кожному своя роль (`ADMIN`, `INVENTORY_MANAGER`, `STAFF`); сторінка «Staff» в адмінці (додати, змінити роль, прибрати; заклад завжди має хоча б одного адміна); зміна пароля
- [x] **Gateway як BFF:** вхід за authorization code + PKCE, токени лише в сесії gateway (браузер має HttpOnly cookie), оновлення токенів, CSRF, вихід і з gateway, і з Identity
- [x] **Сервіси перевіряють JWT і роль у закладі** з `X-Tenant-Id` (спільний модуль `security-support`); заклад, якого немає в токені, → 403
- [x] **Platform API** — лише для адміна платформи; «New venue» бачить тільки він
- [x] **Order → Inventory** зі своїм токеном (client credentials, scope `internal`)
- [x] Адмінка: вхід, повернення на ту саму сторінку, меню й сторінки за роллю, перемикач лише своїх закладів
- [x] Тести: `IdentityServiceIntegrationTest` (9, повний OAuth2-вхід), `InventorySecurityTest` (5), доступ в `OrderServiceIntegrationTest` (+3)

**Частина 2 — гості: готово**

- [x] **Токен гостя:** QR → `POST /api/v1/table-sessions/join` → Order просить Identity (своїм сервісним токеном) підписати гостьовий JWT (заклад, візит, гість, 12 год) замість `X-Participant-Id`; повторне сканування з токеном — той самий гість і рахунок
- [x] **Захист QR:** новий гість `PENDING` — його замовлення зберігаються з зафіксованою ціною, але не йдуть на кухню/бар і не списують склад, доки офіціант не підтвердить гостя в рахунку столика («N to confirm» на сторінці Visits); відхилений гість — замовлення скасовані, більше замовляти не може
